# SVX Roadmap

SVX is built in phases, following the development order in the product specification. The security architecture comes first and the website comes last.

A task-by-task checklist for each phase is in [phase-checklist.md](phase-checklist.md).

| Phase | Scope | Status |
|-------|-------|--------|
| **1. Foundations** | Threat model; security architecture; crypto profile; SVX 1.0 binary spec; Rust parser and writer; STREAM AEAD, HPKE envelopes, Ed25519 signing; deterministic test vectors; property tests and fuzz targets; `svx keygen / pack / inspect / verify` | ✅ done |
| **2. Managed service** | `svx-server` (axum + PostgreSQL). Org registry with DNS TXT domain verification and signed registry records. `svx-oidc` token validation (issuer, audience, signature, expiry, freshness, nonce; JWKS cache; asymmetric algorithms only). `svx-mock-idp` dev IdP (auth code + PKCE). Policy engine: users, groups, `acr` assurance, time window, max age. Server-side expiry and revocation. Key release with ephemeral-key re-sealing, nonce-bound tokens and single-use transaction IDs. `svx-keyagent` recipient key agent. Hash-chained, append-only audit log. Admin API. | ✅ done |
| **3. Client & CLI** | `svx-client` library and the `svx` CLI. `init` pins the registry key. Browser login via OIDC + PKCE with a loopback redirect (RFC 8252). `login/logout/whoami` with a short-lived 0600 admin session. Fail-closed `open` that re-authenticates per artifact with a key-bound nonce, uses private temp files, renames atomically and validates file names. Also `status`, managed `pack --recipient`, `revoke`, `policy`, `organizations`, `audit`. Linux, Windows and macOS file-association files. Device-code flow deferred. | ✅ done |
| **4. Demo & SDKs** | `svx-demo run`: a self-checking demo between Acme Security and Example Corp. Eve intercepts, inspects, forges a token and fails to sign in; Alice is authorized; Bob is denied; tampered, expired (client-side and server-side) and revoked artifacts are refused; the audit chain is verified. `svx-demo serve`: a one-command local stack. Shared `svx_client::Client` facade. Python SDK (PyO3/maturin, abi3) and Node.js/TypeScript SDK (napi-rs), each with typed errors, offline and end-to-end tests, and a demo example. Wheels and npm packages ship with signed releases in Phase 6. | ✅ done |
| **5a. Desktop app** | Secure Verified Exchange for macOS, Windows and Linux (Tauri 2 over `svx-client`, see [desktop.md](desktop.md)). Verified first-run setup, protect & send for files and folders (zipped, hardened extraction on open), double-click opening with a live timeline and distinct refusal screens, basic admin (revoke, audit, policies). `.svx` file association and single instance on all three platforms; unsigned installers built in CI. | ✅ done |
| **Post-quantum hybrid** (SVX 1.1) | Suite SVX-1H for every new file: X-Wing (X25519 + ML-KEM-768) envelopes and release sealing, composite Ed25519 + ML-DSA-65 signatures, post-quantum TLS (X25519MLKEM768). Format 1.1 (`key_envelopes_v2`), hybrid registry key kinds, migration 0002, KATs and hybrid test vectors. Older SVX-1 files still open. Protocol v3: grants and registry and service records are signed with hybrid keys too; clients pin the registry key's 256-bit fingerprint. | ✅ done |
| **Maximum strength** (SVX 1.3) | Suite SVX-2 for every new file: MLKEM1024-P384 envelopes and release sealing, Ed25519 + ML-DSA-87 + SLH-DSA-SHA2-256s signatures (all must verify), SHA-512 and HKDF-SHA512. Protocol v4: service, registry and device keys are SVX-2 keys (grants and account requests carry Ed25519 + ML-DSA-87). Backup password: Argon2id 256 MiB, t=4. Migration 0005, ACVP KATs, `max-*` test vectors. SVX-1H and SVX-1 files still open. | ✅ done |
| **5b. In-app administration & key agent packaging** | All organization administration in the desktop app, no web portal: sign-up of a new organization (DNS + IdP proof, first admin), settings, administrators, policies (create/edit/delete), audit (filter, paging, CSV export), revocation, and keys: signing keys in the OS keychain, encryption-key rotation that waits for the key agent. Key agent packaged as a hardened Docker image and a systemd service with `check` and `healthcheck`, built and smoke-tested in CI. See [desktop.md](desktop.md) and [key-agent.md](key-agent.md). | ✅ done |
| **5d. Personal accounts** | Sign in with Google, or with an email address and a password (Phase 6); the app makes the keys (keychain, one encrypted backup). Send by email address through the signed directory. Format 1.2 (several recipients). The sender keeps control after sending: approval before each open (in the app, with an email notice), one-time files, expiry, revocation per person. History and Requests in the app; CLI `account`, `send`, `requests`, `approve`, `history`, `file`. Company setup stays available. See [personal.md](personal.md). | ✅ done (Google OAuth client and Gmail SMTP setup pending) |
| **5c. Website** (deferred) | Public website: product information, account sign-up and app downloads only. It never receives, encrypts or decrypts files; all of that happens locally in the desktop app. Documentation sections. | later |
| **6. Hardening & review** | Round 1 ($0 budget): email + password accounts replace Apple sign-in; Touch ID / password / Windows Hello before the keys are used; auto-update from the SVX service with an SVX-2-signed release manifest plus Tauri's signature; 12 fuzz targets with long local runs; `cargo audit` in a local preflight. Later: compatibility test suite, independent security review, public beta. Signed installers and hardware-bound keys need paid certificates and are not planned. | in progress |
| **7. View-only files** | The sender makes a file view-only: shown only in the app's viewer, protected from screenshots and recording (macOS, Windows), no copy or save, with a watermark. The recipient can ask the sender for permission to share; only then does it become a normal file. Includes tamper checks. See [phase-checklist.md](phase-checklist.md) for what this can and can't stop. | planned |

Future features, not in v1: federation, hardware keys, device posture, HSM integrations, SIEM/DLP/EDR integration, multi-party approval, threshold keys.
